# Connect the external tracker API

InkTrail reads catalog data from Kitsu. Your reading entries and custom lists live in a separate external REST service. The app has no backend server, database, or local entry store. It works with MockAPI or Beeceptor through the same REST contract.

## Included workspace connection

The delivered workspace has a local `.env` configured with the dedicated public demo endpoint:

```dotenv
EXPO_PUBLIC_TRACKER_API_URL=https://ca491042a4a2e9cd0092.free.beeceptor.com
```

Its [Beeceptor dashboard](https://app.beeceptor.com/console/ca491042a4a2e9cd0092) has stateful CRUD rules for `/entries` and `/lists`. Both collections were verified to return `[]` after creation on October 11, 2026. No account or paid plan was created. This endpoint has the free limits described below, including ten total objects and 30-day unclaimed retention. `.env` is ignored by Git; use this URL in Connection or create a new endpoint if you copy the source without the local environment file.

## Recommended for your own tracker: MockAPI

MockAPI's free plan provides one project with two resources, enough for `entries` and `lists`. It requires a free account and one-time resource configuration; it is not a preconfigured, anonymous shared database. [Plan details](https://mockapi.io/).

1. Sign in at [MockAPI](https://mockapi.io/) and create a project named `InkTrail`.
2. Create two top-level resources named exactly `entries` and `lists`. Do not nest one under the other.
3. Use the fields below. Keep the generated `id` field. Start both resources empty; random generated data will not match the app's model.
4. Copy the project's HTTPS base URL from the dashboard. Include any configured prefix such as `/api/v1`, but exclude `/entries` and `/lists`.
5. Open InkTrail's **Connection** screen, paste that base URL, then connect. The app checks both collection endpoints before saving the connection.

The provider creates standard REST routes for each resource and accepts JSON requests. [Official MockAPI setup guide](https://github.com/mockapi-io/docs/wiki/Quick-start-guide).

### Resource: `entries`

| Field | JSON type | Meaning |
| --- | --- | --- |
| `id` | string | Generated by the provider; omit when creating. |
| `mangaId` | number | Numeric Kitsu manga catalog ID. |
| `title` | string | Display title saved from the catalog. |
| `imageUrl` | string | Cover URL; empty string is allowed. |
| `format` | string | Catalog format, such as `Manga` or `Manhwa`. |
| `totalChapters` | number or null | Known total, or `null` when the catalog has no total. |
| `status` | string | `reading`, `planned`, `completed`, `on_hold`, or `dropped`. |
| `progress` | number | Whole chapters read, starting at zero. |
| `listId` | string or null | A custom list's ID, or `null` for no custom list. |
| `createdAt` | string | ISO date/time set when saved. |
| `updatedAt` | string | ISO date/time set when changed. |

Choose Number for numeric fields and String for text fields in the schema editor. Preserve JSON `null` for unknown `totalChapters` and unassigned `listId`; do not use the string `"null"`. The app sends all business fields, so Faker generators are unnecessary.

### Resource: `lists`

| Field | JSON type | Meaning |
| --- | --- | --- |
| `id` | string | Generated by the provider. |
| `name` | string | Custom reading-list name. |
| `createdAt` | string | ISO date/time set when created. |

`src/types.ts` is the source of truth for both models. The app expects each collection response to be a raw JSON array (`[]` when empty), and each successful create/update response to be a JSON object containing its `id`.

## Alternative: Beeceptor without signup

1. Open [Beeceptor's CRUD API creator](https://beeceptor.com/crud-api/) and create a CRUD route with base path `/entries`.
2. On the new endpoint's dashboard, open **Mock Rules**, choose **Create New CRUD**, and add `/lists`. Keep the identifier field as `id` for both routes. Use actual CRUD rules so writes persist; static mock responses do not implement a tracker.
3. Copy the exact HTTPS endpoint URL shown by Beeceptor. Hostname formats vary, so do not construct a domain from an example. Exclude `/entries` and `/lists` from the URL entered in the app.
4. Connect in InkTrail. Both collection GET requests should return arrays. Give CRUD rules priority over any broad response rules that match the same paths.

Beeceptor stores submitted JSON and provides GET, POST, PUT, PATCH, and DELETE. Free storage is limited to **10 objects across all collections**; exceeding the limit removes older records. Use it for a small demonstration. [CRUD documentation](https://beeceptor.com/docs/crud-api/).

The free plan currently allows **50 requests per endpoint per day**. Unclaimed endpoints expire 30 days after creation; claiming extends retention to 90 days from creation. Connecting, refreshing, mutations, and deleting a list with multiple entries all consume requests. [Pricing and retention](https://beeceptor.com/pricing/).

## Configure the app

### In the app

Open **Connection**, paste the base URL, and connect. Only the URL preference is persisted using AsyncStorage. A configured external service stores the actual entries and lists. A connection test verifies readable collections, while the first save verifies the provider accepts writes.

### Through an environment file

From the `inktrail` directory in PowerShell:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Edit `.env`:

```dotenv
EXPO_PUBLIC_TRACKER_API_URL=https://YOUR_PROJECT.mockapi.io/api/v1
```

Replace the entire example URL with the one from your dashboard. Stop the running Expo process and restart with a cleared Metro cache after changing the environment, so transformed environment values are refreshed:

```powershell
npx expo start --clear
```

`EXPO_PUBLIC_` values are included in the client bundle. They are configuration, not secret storage. Do not place private API keys, passwords, or access tokens here. The app's saved connection can be changed from the Connection screen.

## REST contract

All paths are relative to the configured base URL. Request bodies use `Content-Type: application/json`.

| Action | Method | Path | Body |
| --- | --- | --- | --- |
| Read library | GET | `/entries` | None |
| Read current entry before an edit | GET | `/entries/:id` | None |
| Save title | POST | `/entries` | Complete entry without `id` |
| Update chapters, status, or custom list | PUT | `/entries/:id` | Complete updated entry |
| Remove saved title | DELETE | `/entries/:id` | None |
| Read custom lists | GET | `/lists` | None |
| Verify a selected custom list | GET | `/lists/:id` | None |
| Create custom list | POST | `/lists` | `{ "name": "Weekend reads", "createdAt": "..." }` |
| Rename custom list | PUT | `/lists/:id` | Complete updated list |
| Delete custom list | DELETE | `/lists/:id` | None |

Updates send the complete record because some providers replace the entire resource on PUT. A successful DELETE may return JSON or an empty body.

Illustrative entry create body (replace the sample title and `mangaId` with the actual Kitsu record being saved):

```json
{
  "mangaId": 2,
  "title": "Example manga",
  "imageUrl": "",
  "format": "Manga",
  "totalChapters": null,
  "status": "reading",
  "progress": 12,
  "listId": null,
  "createdAt": "2026-10-11T10:00:00.000Z",
  "updatedAt": "2026-10-11T10:00:00.000Z"
}
```

The provider adds `id`. To update this record, send its complete fields with the changed `progress`, `status`, or `listId` to `/entries/{id}`. The app refreshes affected query data after the server confirms a write.

Deleting a custom list first updates its entries to set `listId: null`, then deletes the list. Titles stay in the library. This involves multiple REST requests and is not a server transaction. If a request fails, some entries may already be detached; refresh and retry after the service recovers. Use an external transactional backend if atomic list deletion is required.

## Catalog configuration

The client reads the public [Kitsu JSON:API catalog](https://kitsu.docs.apiary.io/) at `https://kitsu.app/api/edge`. Catalog requests send **`Accept: application/vnd.api+json`**; using a plain JSON Accept header may return HTTP 406.

Example paths (brackets are shown unencoded for readability; the client uses `URLSearchParams` to encode them):

```text
GET /manga?filter[text]=solo&filter[subtype]=manhwa&page[limit]=12&page[offset]=0&include=categories
GET /manga?filter[subtype]=manga&sort=-userCount&page[limit]=12&page[offset]=0&include=categories
GET /manga/:id?include=categories
```

The **All** catalog merges separately requested manga and manhwa results, retaining an independent page cursor for each subtype and removing duplicate IDs. Discovery results are ordered by `userCount`; merged search results prioritize exact, prefix, and contained title matches, preserving provider order for ties and other results. Categories included in the JSON:API response provide genre labels for each related title.

The adapter maps numeric Kitsu IDs, titles, poster images, publication status, synopsis, and chapter totals into the app's `Manga` type. `averageRating` uses a 100-point scale and is converted to the displayed 10-point score. Unknown chapter totals remain `null`; author credits are optional and are not fetched by this adapter. The stored `mangaId` always identifies a Kitsu manga resource. Do not import IDs from another catalog into this tracker without explicitly mapping them.

Public catalog reads need no app API key. InkTrail uses Kitsu only for catalog retrieval; all tracker writes go to the configured MockAPI or Beeceptor service. A shared queue spaces catalog requests about 1.05 seconds apart as a courtesy, and search is debounced. This pacing is an app choice, not a claimed Kitsu rate-limit allowance. Cancelled requests and temporary service failures are handled by the HTTP client. Retry after a displayed network or rate-limit error.

## Manual verification

Use a dedicated test endpoint and inspect its dashboard while you:

1. Connect and confirm GET `/entries` and GET `/lists` return arrays.
2. Search for a title and save it. Confirm POST `/entries` and the new server-assigned ID.
3. Change progress and status. Confirm PUT `/entries/:id`; reload the app and confirm those values return from GET `/entries`.
4. Create a custom list, rename it, and assign a saved title. Confirm POST/PUT `/lists` and PUT `/entries/:id`.
5. Delete the custom list. Confirm entry updates precede DELETE `/lists/:id`, and the title remains saved without a list.
6. Remove the title and reload. Confirm DELETE `/entries/:id` and that it remains absent.
7. Disable networking or use an invalid endpoint. Confirm a clear error is shown and no successful save is claimed.

## Troubleshooting and scope

- **Catalog works, library does not:** Kitsu and the tracker are separate services. Configure a writable tracker endpoint.
- **404 or non-JSON response:** Check the base URL and resource names. Do not paste a dashboard URL or append `/entries` to the base.
- **Connected but save fails:** Confirm POST/PUT/DELETE are enabled and check provider quota. The connection test only uses GET.
- **Records disappear on Beeceptor:** Check the shared ten-object limit and endpoint retention.
- **Unexpected generated records:** Clear only your own test resource data in the provider dashboard and start with empty collections.
- **Browser-only network error:** Ensure a replacement provider allows CORS for your web origin and the required methods and headers. Native apps do not enforce browser CORS.

These endpoints are public demonstrations, with one library per endpoint and no account isolation. Use a dedicated endpoint and non-sensitive test data. A production version should keep this frontend-to-REST architecture while moving authentication, user ownership, validation, uniqueness, and atomic operations into an external API service. Client validation helps the interface; it does not secure a public endpoint. Two clients can still create duplicates or overwrite each other's updates without server-side constraints.
